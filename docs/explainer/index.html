Brenn, explained

A guided tour of Brenn's architecture for someone who has not read the code. It describes the repository as of commit 2a286d46, not a roadmap.

The project's own one-line answer, written for infrastructure people first:

Brenn is a self-hosted application framework for the LLM era: a capability-sandboxed WASM component host and a pub/sub message bus, written in Rust, where LLM agents are first-class bus citizens with the same grants, ACLs, and rate limits as compiled code. It runs at personal/household/small-team scale, and it panics rather than do the wrong thing. README.md, "What Brenn is"

The claim this page sets out to earn:

Brenn is a self-hosted application framework for a world where most code is written by LLMs and reviewed lightly. It runs that code — compiled WASM components and LLM agents alike — inside capability sandboxes, connects them through a message bus that models channels as recent history rather than as obligations, and refuses to do the wrong thing rather than tolerate a bug.

(One refinement to the README's sentence comes in the agents section: agents and components share one authority vocabulary and one policy type, each enforced at its own seam; their rate-limit mechanisms are not identical.)

The README says what it is good and bad at. Good at: personal-assistant applications; assistant applications with customized UI, "so that not everything is typing in a text box"; automations of all sorts. Bad at: being an agentic coding environment ("wouldn't you rather use Claude Code?"), and being a web-scale platform — "this thing will not scale beyond family/workgroup/small-team levels". If that last line rules Brenn out for you, it is the most useful sentence on the page.

The tour: the problem · the system on one screen · the bus · components in the sandbox · LLM agents · two user interfaces · transports · better dead than wrong.

The problem Brenn is built for

Imagine a personal assistant that wants to write an automation for you — something about the lights, or filtering email, or fetching a weather report. The assistant is an LLM; it can write that code. You are not going to review it carefully. The point of an assistant is to make your life easier, so you will run what it wrote with minimal review, if any. The only honest response is to run that code somewhere its bugs cannot do much damage.README.md, "Going deeper"

That argument does not depend on who wrote the code. Human-written code has security bugs too; that is why breaches made the news before LLMs existed. It also applies to Brenn itself, most of which is LLM-authored under an adversarial review workflow. So Brenn hosts as much of its own machinery as it reasonably can in the same sandboxes it offers to everyone else. Two in-tree examples come back later: the policy deciding when a long-running agent's conversation should be recycled (conversation-recycler), and webhook replay protection (replay, replay-generic). Both are WASM guests, not host code.README.md, "How Brenn itself was developed"; brenn-wasm/deployed-components.txt

The stance that follows, in the README's words: "lock it down, don't trust it, no matter who wrote it."

The whole system on one screen

A browser talks to a Rust backend over websockets; the backend runs Claude Code as one subprocess per conversation and hosts WASM components; a message bus inside the backend connects all of them to each other and to the outside world. Every box below carries the trust decision the security posture document makes about it. The colours are those tiers: blue is fully trusted (the operator, and the backend as the trusted computing base), teal is sandboxed-trusted, green is authenticated but bounded, amber is semi-trusted, red is untrusted; grey boxes carry no tier of their own.

The asymmetry to notice is the one the posture document asks every reviewer to internalize: "we launched it" (Claude Code) and "it's our code" (in-tree WASM) do not confer trust in the content that crosses the boundary.

The bus: channels are history, not obligations

Most messaging systems are built around a transfer of custody. A message belongs to someone; it is handed to a broker; the broker owes it to a consumer; an ack settles the debt and the message ceases to exist. Brenn's bus rejects custody entirely:

A channel is not a conduit for messages in transit. It is a rolling window over a time series that simply exists. The last N messages published to a channel are there. They are there whether anyone subscribed, whether anyone read them, whether anyone ever will.docs/message-bus.md, section 1

Nothing consumes. Reading does not remove. There are no acks, no redelivery, no at-least-once promise, no dead-letter queue — Brenn has none of the machinery those words name, and the rest of this page does not use them.

No backpressure, as a structural fact

Backpressure only propagates where downstream capacity constrains upstream acceptance, and that constraint only exists when delivery is an obligation. Remove the obligation and there is nothing for pressure to act on. This fits the domain because the producers are exogenous: the dishwasher finishes, email arrives, someone speaks into a microphone. None of them can be told to wait. And every queue is bounded in the end — a system that pretends otherwise gets killed for memory or runs out of disk. So Brenn drops the oldest message and increments a counter, so that the loss is visible.

N is a count; reason about it as duration

A channel has one parameter, its depth N. The same N means wildly different things at different rates:

ChannelRateNHorizon
power.dishwasher.finished~1/day100~3 months
mail.arrived~200/day100~12 hours
sensor.temperature.kitchen1/min1010 minutes

The design-time obligation is not "pick a number" but "pick the outage you intend to survive, then multiply."docs/message-bus.md, section 2.1

A subscription has two knobs, and they are independent

push_depth — what wakes me. Purely about activation. Zero means "never activate me on this channel". Five means "activate me on new messages; if a burst arrived while I was busy, coalesce the pending activations into one and hand me at most the five most recent."

retain_depth — what I can see. Purely about visibility: a private window of the most recent M messages, never more than the channel holds (boot refuses a subscription that asks for more). It does not cause activation; a subscriber with push_depth=0, retain_depth=50 sees fifty messages and is never woken by any of them.

Coalescing is the default, not a degradation path: five temperature readings while you were busy should wake you once, with the current temperature. Where a subscriber needs to know it skipped something, its own drop counter says so. The counter is charged only for unseen messages that fell out of the subscriber's retained window, so an under-sized push_depth is silent while an under-sized retain_depth is not. Every subscriber has its own position; one can drop while another does not, and the channel's contents are identical whether it has zero subscribers or fifty.docs/message-bus.md, sections 2.2–2.3

A subscription coming into existence is a delivery point: it is owed up to push_depth of the retained window, immediately, as unseen. A late joiner does not arrive to an empty pipe; it simply looks.

Time and state are not subsystems

A message may carry a delivery time, deliver_after. That one mechanism is the substrate for every timer, timeout, retry, debounce and scheduled reminder: a component schedules its own future activation by publishing to a channel it also subscribes to. There is no scheduler subsystem and no cron. Likewise, because channels persist independently of reading, a retained channel is a state variable: current state is retain_depth=1 on the channel that carries it. There is no separate key-value store.docs/message-bus.md, sections 2.4 and 2.5

Signals and facts

The model forces one question at design time: does message N+1 subsume message N? Signals — temperature, presence, bulb state — do: the newest contains everything the older ones did, and dropping old is the semantically correct operation. Facts — dishwasher finished, email arrived, "cancel the 1:1" — do not: missing one means a side effect that never happens. The bus cannot enforce the distinction. What makes fact channels safe is not a delivery guarantee but "a window horizon that exceeds the worst outage you intend to survive." The alternatives are an unbounded queue ("a promise the universe will not honor") or backpressure ("you cannot tell the dishwasher not to finish"). And the idiom that softens the rest: pair a fact channel with a state channel, so an agent that was down reconciles against current state instead of replaying history it no longer has.docs/message-bus.md, section 3

Why this fits graphs of agents

Late joiners are first-class: an automation written at 3pm subscribes to a channel that already has history. Observers are free: a logger, a debugger or an LLM asked "why did that happen?" is an ordinary subscriber that costs the channel nothing. LLMs want windows, not messages: retain_depth is a context window expressed in the transport. And because subscriptions are declarative and the channel is oblivious to them, an agent that writes automations is adding edges to a graph, not negotiating delivery contracts; "stop doing that" removes an edge, with nothing to drain.docs/message-bus.md, section 4

Two more axes

Channels are ephemeral (in memory, ephemeral:) or durable (disk-backed, brenn:) — a statement about whether history survives a restart, not about delivery. Separately, channels are transportable or not: ephemeral: and brenn: channels can extend across the wire; local: channels never leave the host that holds them.docs/message-bus.md, section 2.1

Components in the sandbox

A Brenn component is a WebAssembly component targeting a WIT world. The general world is brenn:processor: a component exports one function, receive(activation), and may import up to ten host interfaces — ports, store, log, alert, config, mqtt, tools, calls, dom, page-dom. (There is also a narrow brenn:replay world for webhook replay checks, importing only store and config and exporting check; the replay guests implement it, conversation-recycler implements the general one. The rest of this section is about processor.)brenn-wasm/wit/processor.wit; brenn-wasm/wit/replay.wit

What is not in the world matters more:

  • no filesystem;
  • no sockets, no HTTP egress;
  • no clock — time arrives as a host-stamped now on the activation;
  • no secrets;
  • no WASI at all.

The only persistence is the transactional store; the only outbound network is the MQTT broker via mqtt and whatever tools the operator granted.

Deny-by-default is structural. The operator's grants list decides which interfaces are linked at all. An artifact that imports an interface its instance was not granted fails at load with a named diagnostic.brenn-wasm/src/lib.rs

A guest publishes by port name, never by channel address. The operator's bindings decide where a port goes, and a publish outside the output ACL comes back as a typed not-permitted.

Each activation is a fresh instance. Linear memory lives for one activation. State is kept by publishing it to a retained port — the retain_depth=1 idea from the bus section, showing up again.

Resource limits are real wasmtime limits on a backend-placed component: fuel per activation, a wall-clock deadline per activation, a memory cap that traps on over-growth, plus per-activation quotas on log, alert and tool calls.

The constants, as of commit 2a286d46
  • Fuel: the larger of 50,000,000 and 10,000,000 per delivered envelope.
  • Deadline: 300 epoch ticks of 100 ms (30 s).
  • Memory: 16 MiB; tables capped at 65,536 elements.
  • Per activation: 256 log calls, 4 alert calls, 64 fast tool calls.
brenn-wasm/src/lib.rs (the PROCESSOR_* constants)

Two placements, one class. The same component class, with the same activation type, can be placed at the backend top level (a consumer) or inside a browser surface. The class, the activation contract and the channel semantics per scheme are identical; a host-conformance suite pins that channel hosting, not merely admissibility, is the same for every scheme a host binds. The sandbox is not identical: the wasmtime limits above are backend facts, and a surface-placed module runs unsandboxed in the page's JavaScript realm, where the separation is bug containment only.docs/config-dsl.md, "Surfaces"; docs/message-bus.md, section 2.1.1

Out-of-tree components are first-class. The WIT world is an external contract, and its evolution is additive-import-only: "a new capability is a new interface, and no existing shape moves."brenn-wasm/wit/processor.wit

LLM agents on the same bus

An agent is a Claude Code subprocess per conversation, spawned with --permission-mode auto and a stdio permission prompt, optionally inside a podman container whose secrets never appear on a command line.brenn-cc/src/session/mod.rs

How an agent reaches the bus. Through tools — MessageSubscribe, BrennSend and friends — that Claude Code sees via a no-op MCP server and that Brenn intercepts with PreToolUse/PostToolUse hooks; "the real work happens in the Brenn server". The agent's acl subscribe and acl publish matchers are checked by the same policy type, and the same predicate, that a WASM component's bindings resolve to — enforced at the agent's own seam rather than the component's. An agent may not bind local: at all: "a confined channel has no delivery path to an agent". Rate limiting differs in mechanism: an agent draws on a per-conversation send budget and per-channel send rates; a component on per-sink token buckets and per-activation budgets. One authority vocabulary, one policy, each enforced at its participant's seam.noop_mcp.py; brenn-lib/src/messaging/gates.rs; brenn-dsl/src/derive.rs

How a message wakes an agent. The bus notices a subscribed channel moved. If the conversation has no running process and the message's urgency clears the subscription's wake_min, Brenn spawns Claude Code (resuming the prior session) and injects the unseen messages as one user-role turn wrapped in a <brenn-messages> tag, so the model can tell host-injected turns from the human. A burst costs one turn, not forty — coalescing again.brenn-server/src/messaging_router.rs; brenn-render/src/system_message.rs

What stops two agents talking forever. The impetus pool. Every injected turn draws one unit from a per-conversation stock, and only evidence of live user interaction can refill it: "Nothing an LLM, a WASM component, or a transport ingress can reach mints impetus." A loop of bus legs depletes the pools it runs on and halts. Exhaustion holds the batch; it does not drop it.brenn-server/src/active_bridge/impetus_pool.rs

The approval gate, as it actually flows

Every tool call Claude Code proposes passes three authorizers, in this order.

  1. Brenn's PreToolUse hook. Brenn observes and grants nothing — with one exception: Brenn's own intercepted tools (bus tools, automations, push, MQTT, display) are no-ops on Claude Code's side, and Brenn answers the hook for those because it performs the effect itself, under the app's grants and ACLs. For every other tool the hook returns no opinion. No operator rule runs here.
  2. Claude Code's auto permission mode. Claude Code's own classifier approves the calls it judges safe.
  3. The stdio permission prompt. Whatever Claude Code still asks about arrives in Brenn's permission handler, which auto-approves it if it matches a hardcoded read-only set or an operator rule — three layers (config file, app-wide, per-conversation), anchored regular expressions, approve-only: a rule can allow, never deny. Anything else goes to a human in the approval dialog.

brenn-server/src/active_bridge/approval_dispatch.rs; brenn-cc/src/protocol/builders.rs; brenn-approval-rules/src/lib.rs

Two policies from the security posture hold across all three:

Observation is not authorization. Hooks or interception points that merely observe a tool call must not be repurposed into granting permission; doing so can bypass the real permission decision.

What executes must equal what was approved. When a human approves an action, the action that runs must be the one displayed and approved.docs/security-posture.md, section 7.3

Stage one is the first policy honoured, not broken: the hook grants nothing it does not execute itself, and a regression test pins that even read-only tools get no opinion from it. (The same section's two-item list of authorizers — operator rule or human — predates auto mode; the code has three, as above.)

Brenn's own guts in WASM. When a long-lived agent's context should be recycled is decided by a replaceable WASM policy component, conversation-recycler, publishing on an epoch channel. The host decides nothing: it only records which epoch each agent's current conversation must carry.brenn-conversation-epoch/src/lib.rs

One tool vocabulary. The same tool / allow / rate_limit statements appear inside an agent body or a component body and resolve into the same grant map.docs/config-dsl.md, "Tool grants"

Two user interfaces, one rule

The chat UI is TypeScript and Lit custom elements. The backend renders HTML; the browser sets it. Every message type is a Rust struct with its TypeScript generated by ts-rs. The LLM does not generate UI: it selects from a catalogue of hand-built components through virtual tools — the approval dialog, AskUserQuestion, pfin's reconcile cards and batch tables, the artifact pane via DisplayFile, the task list. Users build muscle memory because the components do not change shape under them.brenn-render/src/approval_formatter.rs; brenn-ws-types/src/lib.rs

Direct manipulation does not go through the LLM. Clicking "done" on a task sends a typed TodoDone message; the backend runs the graf CLI; the browser gets a typed result. The LLM is told only if it failed. That is the README's "it's easier to click 'done' on a to-do list item than to tell the LLM to mark it done", with code behind it — and the LLM can still mark it done for you.brenn-server/src/routes/ws/todos.rs

Surfaces are the newer UI: Rust compiled to WASM, running in the page. A surface is a page — transport grants, a skin, and component instances — declared in config. One privileged chrome component owns layout and is the only thing that may touch DOM outside its own subtree; every other component renders into its own wrapper through an allow-listed dom interface where text reaches the page as textContent, never as HTML. The websocket carries the same attachment protocol a remote daemon speaks, whose vocabulary names "no component, port, instance, DOM, or pixel".surface/contract/src/lib.rs; attach/proto/src/lib.rs

The in-tree bar surface, as configured: three Protobar panels that an agent writes to with BrennSend, a Meeting panel that escalates from ambient to overdue on its own clock, and a headless ModeClock driving dark and light themes.

surface bar {
  grants = [subscribe, publish];
  skin = "bench";
  new p1: Protobar { grants = [ports, log, dom]; in messages <- bar_a; … }
  new p2: Protobar { grants = [ports, log, dom]; in messages <- bar_b; … }
  new p3: Protobar { grants = [ports, log, dom]; in messages <- bar_c; … }
  new mode: ModeClock {
    grants = [ports, log, dom];
    in config <- bar_mode { push_depth = 1; }
    out theme -> "local:brenn/theme";
    …
  }
  new meeting: Meeting {
    grants = [ports, log, takeover, dom];
    in agenda <- bar_agenda { push_depth = 1; }
    out takeover -> "local:brenn/takeover";
    …
  }
}

Talking to the world

Webhooks. Per-endpoint HTTP routes with four signature schemes: raw-body HMAC (GitHub, Forgejo), timestamped HMAC (Slack), Stripe's t=…,v1=…, and bearer token. Unknown key ids get timing parity with known ones. Replay protection is optional and runs as a WASM guest. Scheme: webhook:<slug>.brenn-webhook/src/lib.rs; brenn-lib/src/webhook/scheme.rs

MQTT. One session per configured client; inbound topics fan out to every matching channel filter; outbound shares one gate chain between the LLM's tool and the WASM host function. In practice Home Assistant is the device-driver library — it gets thousands of devices speaking MQTT and JSON — and Brenn takes it from there, with WASM components handling the routine automations and LLMs stepping in where judgment is needed. Scheme: mqtt:<client>:<topic>.brenn-server/src/mqtt_router.rs; brenn-mqtt/src/egress.rs; README.md, "A note about Brenn vs Home Assistant"

PWA push. Notifications encrypted per RFC 8291, gated by the app's pwa_push grant and the same send budget agents draw on. Scheme: pwa_push:<user> or pwa_push:<user>@<device>.brenn-pwa-push/src/lib.rs; brenn-pwa-push/src/targets.rs

Remote attachers. A native daemon acts as one principal, remote:<slug>, with exactly the channels the operator wrote for it.brenn-remote-server/src/lib.rs

Not there

  • Discord, Telegram and Matrix transports.
  • Peer-to-peer federation between Brenn servers.
  • LLM harnesses other than Claude Code.
  • A guide to a first deployment.

Better dead than wrong

The backend principle, in the security posture's words: the backend "must never do the wrong thing. It fails fast: it shuts itself down rather than tolerate a bug or proceed past an unexpected condition. No fallbacks, no swallowed errors". Transient failures, such as an API briefly unavailable, are handled normally; they are not unexpected.docs/security-posture.md, section 1

One concrete case: if Claude Code sends a control request Brenn does not recognize, Brenn cannot answer it safely, so it kills the session and raises an alert rather than answer with a default or a guess. In general, anything sketchy from a browser is a fail2ban signal; anything unrecognized from Claude Code is an alert to the operator's phone, probably meaning a Claude Code upgrade Brenn has to adapt to.docs/security-posture.md, section 7.2; brenn-cc/src/error.rs

Status, in the README's words

  • The engine is mature. Backend, the messaging bus, the WASM host and capability model, grants/ACLs/rate limiting, MQTT/webhook/Push ingress and egress, auth, the Claude Code integration — real, tested, in daily use.
  • The WASM-in-the-browser "surface" UI is young. The framework under it is solid (frozen wire protocol, its own security model, well tested). The applications on top are thin — right now the flagship demo is a little bar touchscreen monitor that sits on my desk under my main monitor, and already that's made my life way better.
  • Smart home stuff is the current development frontier/focus. This is my highest priority right now for myself: Bring up a Brenn-connected smart speaker/voice assistant, plus other sensor pods: mmWave radar (presence sensors) and a camera pipeline, plus Home Assistant interfaces.
  • Getting-started docs are not done. You can build and run it (make build, make launchdev), but standing up a real configuration is currently more archaeology than onboarding. The configuration language itself has a prose reference — the config DSL document — and one operational flow has a guide of its own, Claude accounts: profiles and switching, but there is no guide to a first deployment. It's not ready for anybody who doesn't know what they're doing to host it yet. I'd just rather not pretend it's turnkey. So if you were looking for the install guide, there isn't one. (Your LLM can figure it out though, even if you can't.)
